## Результат этапа

Пользователь включает тайлинг горячей клавишей. На выбранном мониторе одно
главное окно занимает левую колонку, остальные размещаются справа. Появление,
закрытие и временное скрытие окон обновляют раскладку. Выключение останавливает
управление и запускает восстановление сохранённых позиций подходящих окон.

Выбранный монитор определяется при включении по foreground window; если его
нет — используется основной. Окна других мониторов не переносятся. Переключение
активного приложения не меняет выбранный монитор и порядок окон.

В этом этапе остаются обычные рамки, отдельная команда управления фокусом не
нужна. Анимации, BSP, воркспейсы и полный язык конфигурации идут следующими этапами.

## Модель и границы модулей

| Модуль | Ответственность |
|---|---|
| layout.hpp / master_stack.cpp | Реализовано: Rect, min/max/step, solver, LayoutInfeasible, бюджет уточнений |
| managed_windows.hpp/.cpp | Реализовано: стабильный порядок, availability, floating, interactive move, Master |
| geometry.hpp/.cpp | Реализовано: чистые insets, visible↔outer, DIP, безопасный fit control rect |
| monitor_context.hpp/.cpp | Реализовано: выбранный монитор, rcWork, DPI, revision и уведомления |
| window_geometry.hpp/.cpp | Реализовано: проверяемый read-only снимок outer/visible/placement/state |
| window_actuator.hpp/.cpp | Реализовано: jthread, stop_token, bounded requests/results, leases/session, async SetWindowPos |
| layout_controller.hpp/.cpp | Реализовано: canonical targets, версии, acknowledgement, сроки ожидания, retry, refinement |
| control_window.hpp/.cpp | Реализованы hidden PMv2 HWND и WM_DISPLAYCHANGE/SETTINGCHANGE/DPICHANGED; hotkeys впереди |

WindowId не равен HWND: это монотонный номер жизни окна, который не переиспользуется.
В текущем bridge WindowId равен существующему generation из WindowRegistry;
второго независимого счётчика идентичностей нет. Новый HWND lifetime получает новый ID.
ManagedWindows принимает новые ID только выше ранее принятых; закрытый ID нельзя
воскресить поздним admit. Первоначальный порядок — порядок admission, затем он
меняется только явной командой. Повторное наблюдение, rename, rescan и Z-order
порядок не меняют. Операции с закрытым ID отвергаются.

Команда содержит WindowId/generation, HWND и ожидаемые PID/TID.
Ядро проверяет актуальность generation, исполнитель повторно проверяет
идентичность и состояние непосредственно перед действием. Закрытие удаляет
отложенные команды. Это уменьшает гонки, но не создаёт атомарную идентичность Win32.

Состояние Pending запрещает новые команды до успешного чтения свойств,
даже если диагностический реестр сохраняет прежнюю видимость для логирования.
Текущее поле eligible в реестре само по себе не разрешает перемещение.
Реализованный реестр уже передаёт Pending/Inactive/Ineligible в ManagedWindows.
Режим Tiled/Floating независим от availability и interactive_move; только Ready
Tiled вне ручного перемещения участвует в layout_windows(). Снимок владеет данными.
Min/max/step задаются явно: модель не выводит ограничения из одиночного observedRect.

## Раскладка и геометрия

- Вход solver: физическая рабочая область монитора, gaps в физических пикселях
  после преобразования из DIP, master ratio и упорядоченные WindowId с необязательными
  min/max ширины/высоты и известным step/base для каждой оси.
- Начальные параметры: один master, доля 60%, внешний и внутренний gap 8 DIP.
- Ноль окон → пустой результат. Одно → вся доступная область с внешним gap.
  Два и более → master слева, stack справа.
- Вычисления промежуточных размеров — int64_t. Перед Win32 проверяются диапазоны.
  Отрицательные координаты монитора допустимы.
- Высоты распределяются bounded water filling: общий уровень с индивидуальными
  min/max; остаток получают первые незаполненные cells. При достаточных maximum
  последняя ячейка заканчивается на границе доступной области. Если все окна
  достигли maximum, оставшаяся область снизу пуста — ограничения не нарушаются.
- Минимумы ширины корректируют долю master к ближайшему выполнимому разделению.
  Максимум ширины ограничивает окно внутри колонки, оставляя свободное место.
  Сумма минимумов высоты с gaps или минимумов колонок, превышающая область,
  даёт LayoutInfeasible с пустым placements, без частичного результата.
- Некорректные параметры и недостаток места возвращают ошибку до отправки команд;
  прямоугольники с неположительными размерами не выдаются.
- Рабочая область берётся из MONITORINFO.rcWork, поэтому учитывается панель задач
  с любой стороны. Доступность и topology монитора перепроверяются при изменениях.
- Процесс остаётся PerMonitorV2. DPI целевого монитора читается через собственное
  PMv2 control window на этом мониторе. DPI чужого DPI-unaware окна может быть
  96 и не подходит для определения масштаба целевого монитора.
- При выборе монитора hidden control window помещается внутрь физического
  MONITORINFO.rcMonitor, включая отрицательный origin. Размер служебного HWND
  ограничивается размерами монитора; выбранная точка, например центр, не лежит
  на границе. Перед GetDpiForWindow проверяется MonitorFromWindow == выбранный
  HMONITOR. Несовпадение оставляет monitor_context неготовым.
- При WM_DPICHANGED lParam RECT копируется до выхода из WndProc. Suggested rect
  применяется к собственному окну с NOACTIVATE/NOZORDER, с ограничением размера
  и положения внутрь выбранного rcMonitor; затем проверяются monitor и DPI.
  При смене topology сведения перепроверяются. Отказ API или несовпадение device
  name выбранного HMONITOR очищает snapshot; refresh не выбирает primary сам.
  Повторная явная команда select_for_window(nullptr) выбирает primary; вызывающий
  код передаёт GetForegroundWindow() явно, если нужен выбор по активному окну.
- GetDpiForMonitor не является запасным вызовом из PMv2-потока: его документация
  рекомендует GetDpiForWindow для per-monitor-aware контекста. Причина выбора —
  контракт awareness и WM_DPICHANGED, а не экономия зависимости Shcore.

Результат solver содержит slot и target. Slot — ячейка раскладки, target —
канонический видимый прямоугольник окна, привязанный к верхнему левому углу slot.
Известный step задаёт длины base + k * increment, k >= 0. Target округляется вниз
к допустимой длине, но не ниже minimum; непомещающийся минимум даёт LayoutInfeasible.
При target 294 внутри slot 300 остаётся 6 px свободного места. Solver никогда не
изменяет входные constraints и не запускает обратный пересчёт из своего результата.

Адаптер измеряет GetWindowRect и
DWMWA_EXTENDED_FRAME_BOUNDS в согласованных физических координатах и переводит
их в требуемые outer bounds. Для каждой стороны:

```text
targetOuter.edge = targetVisible.edge + currentOuter.edge - currentVisible.edge
```

После изменения DPI/рамок отступы перечитываются. Если достоверный снимок
получить нельзя, действие откладывается. Заголовки и стили не изменяются.

### Контракт реализованного чтения и конвертации

WindowGeometryReader требует PMv2-поток и ожидаемые HWND/PID/TID. Три чтения
состояния окружают две полные пары outer/visible/WINDOWPLACEMENT. Проверяются
идентичность, visible/iconic/zoomed, стили, root/owner, DPI и cloak. Неизменность
outer, visible и полей placement проверяется точно; tolerance относится к будущему
подтверждению команд, а не к принятию смешанного снимка.

DWMWA_EXTENDED_FRAME_BOUNDS и CLOAKED принимаются только при HRESULT == S_OK.
S_FALSE тоже не даёт snapshot. Hidden/minimized/cloaked/maximized неactionable;
минимизированные координаты не используются. wp.length устанавливается перед каждым
GetWindowPlacement; возвращённая длина, showCmd и положительные ограниченные
размеры rcNormalPosition проверяются. Его workspace-координаты сохраняются без
сопоставления с rcWork. При любом отказе optional snapshot пуст, коды ошибок сохранены.

Повторное чтение обнаруживает переходы, но не превращает Win32/DWM в транзакцию:
ABA-переходы и same-thread HWND reuse между проверками остаются ограничением.
Перед будущим действием контроллер обязан проверить generation и свежесть контекста.

Insets измеряются как visible.left - outer.left, visible.top - outer.top,
outer.right - visible.right, outer.bottom - visible.bottom. Любая отрицательная
дельта или visible за пределами outer отвергается как неподдержанный custom frame;
отступы не обрезаются молча. Вычисления int64_t проверяют int32 координаты,
положительные размеры и допустимые для Win32 extents. Visible target обязан
лежать в rcWork; расширенный outer может выступать невидимой рамкой.

Кэша frame insets пока нет: каждое чтение/preview измеряет их заново. MonitorState
revision меняется на DPI/display/settings уведомлениях даже при возврате метрик
к прежним значениям. Ошибка DPI handler очищает snapshot; более поздний refresh
может восстановить Ready. Этот revision станет ключом инвалидации кэша на шаге 4.

Опция --preview-layout строит Master-Stack для Ready окон выбранного монитора,
переводит все targetVisible в targetOuter и только затем печатает план. Неactionable
окна исключаются; невалидный снимок откладывает весь preview. Принадлежность окна
монитору проверяется до и после чтения и перед публикацией плана; monitor revision
перепроверяется. Это диагностический снимок, не обещание атомарного desktop state.

## Применение и обратная связь

Начальный путь — отдельные SetWindowPos с SWP_NOACTIVATE | SWP_NOZORDER |
SWP_NOOWNERZORDER | SWP_ASYNCWINDOWPOS. Пакет DeferWindowPos можно добавить
после проверки основной логики; атомарность кадра DWM от него не предполагается.

На окно допускается одна ожидающая подтверждения команда и одна последняя
желаемая цель. Хранятся версия layout, targetOuter, observedOuter, срок ожидания
и число попыток. Идентичные цели не отправляются повторно. LOCATIONCHANGE
перечитывает геометрию: совпадение подтверждает команду, не запускает такой же layout.
Сравнение граней выполняется в int64_t с допуском 1 физический px на грань;
2 px допускается только явной настройкой совместимости. Саморасширения допуска нет.
Наблюдение не заменяет каноническую цель, поэтому ошибки округления не накапливаются.
Outer acknowledgement и корректность visible target проверяются отдельно;
пересечения окон и выход за рабочую область не становятся допустимыми из-за tolerance.

Начальная политика исполнения: подтверждение до 500 мс после успешной отправки,
не после постановки в очередь. Не более одной повторной отправки после проверки
актуальности и состояния приложения. Ошибка API, отсутствие подтверждения и
устойчивое ограничение размера — разные результаты. Timeout не переводит окно
автоматически во floating и не доказывает min_size.

Устойчивый clamp вверх после проверки контекста может уточнить минимум. Стек
пересчитывается целиком: 400/250/250 вместо 300/300/300; следующий минимум 280
может дать 400/280/220. WM_GETMINMAXINFO даёт tracking hints, не универсальную
гарантию программного resize. Ограничения проверяются по наблюдениям и привязаны
к generation/DPI/ширине/оформлению; смена контекста инвалидирует learned cache.

Одна внешняя эпоха получает max(1, число окон в стеке) каскадных пересчётов.
Реализован ConstraintRefinementBudget; его экземпляр хранит LayoutController.
Каждая принятая партия уточнений перед re-solve потребляет одну попытку. Версия
команды, timeout, LOCATIONCHANGE и сам пересчёт не создают новую эпоху и не
сбрасывают бюджет. Новая эпоха возникает при изменении набора окон/topology или
явном действии пользователя. Исчерпание завершает процесс как LayoutInfeasible
с причиной RefinementLimitReached; это предел уточнения, не доказательство
математической невозможности. Смена DPI/revision/стилей/поколения или набора
участников создаёт внешний контекст и инвалидирует learned cache. Insets
фиксируются для контекста: колебание DWM на 1 px не создаёт новую эпоху. Learned
height также инвалидируется при изменении ширины целевого visible.

Уменьшенный размер (300 → 294) никогда не повышает minimum. Известная сетка уже
учитывается чистым solver. Неизвестный step нельзя вывести из одного снимка:
устойчивое уменьшение требует отдельной классификации constrained/unknown,
проверки containment и отсутствия пересечений. Контроллер может сохранить такое
окно внутри slot с диагностикой без повторов этой цели в текущей эпохе. Это
не обычное подтверждение equality и не переписывание canonical target в observed.
Неопределённый результат не запускает бесконечный подбор шага или нового минимума.

При LayoutInfeasible не отправляются новые команды группы. Последняя согласованная
раскладка сохраняется, если ещё выполнима; иначе группа приостанавливается с
объяснением. Пользователь может явно вывести окно во floating. Сам автоматический
clamp не приводит к выводу окна поверх соседей.

## Протокол исполнителя

Один std::jthread, ограниченная очередь запросов, mutex и condition_variable_any
со stop_token. Worker получает неизменяемую команду с request_id, session_epoch,
WindowId/generation, HWND/PID/TID, layout_version и targetOuter. Не начатые цели
одного окна коалесцируются; устаревший запрос не переставляется за новую жизнь.
Очередь ограничена, полная очередь возвращает Backpressure. Место под ответ
резервируется при принятии запроса: результаты не теряются при переполнении.

Общий лимит 128 credits включает queued + in-flight + недренированные results.
Coalesced заменяет ещё не начатый запрос с передачей его credit; отдельного ответа
на старый request_id не будет. На shutdown queued запросы получают Cancelled,
исполняющийся запрос завершается своим результатом, затем jthread присоединяется.
Lease относится к одной жизни окна; переход контекста отзывает старые leases.
Новая версия reflow меняет dispatch session, но не сбрасывает внешний бюджет.

Основной поток единолично владеет моделью. Worker освобождает mutex до Win32,
проверяет разрешение/идентичность непосредственно перед вызовом и возвращает
Submitted/Failed/Cancelled. Ответы хранятся в отдельной очереди; PostMessage на
control window — wake без сырых owning pointers; таймер резервно дренирует ответы.
Submitted не означает Applied. Если LOCATIONCHANGE пришёл раньше ответа worker,
controller использует уже имеющийся свежий снимок после submission, а не ждёт
обязательно следующего события. Старый ответ не завершает новую цель/эпоху.

Message loop перед tick перечитывает снимки, в том числе по LOCATIONCHANGE и
250-мс таймеру. submitted_at ставится после успешного возврата SetWindowPos и
начинает deadline 500 мс; issued_at непосредственно перед вызовом задаёт нижнюю
границу свежести снимка. Это учитывает применение ещё до возврата API. Результат
Submitted сам по себе никогда не подтверждает геометрию. После единственного
ретрая min/step классифицируются только по повторным одинаковым снимкам,
стабильным не менее 100 мс, с ожидаемым X/Y. Один уменьшенный снимок не обучает
step или minimum. Terminal stop сохраняется даже через временную ошибку снимка;
новую выдачу разрешает изменение внешней конфигурации.

SWP_ASYNCWINDOWPOS асинхронен при разных input queues и не даёт универсального
таймаута выполнения любого Win32-вызова. Исполнитель отделяется от message loop;
AttachThreadInput не используется. Если испытания выявят зависание исполнителя,
следующим решением будет отдельный broker process, а не TerminateThread.

Отправленную асинхронную команду отменить нельзя. Выключение запрещает новые
команды и инвалидирует цели, но возможное позднее применение учитывается перед
восстановлением сохранённой позиции. Оно также требует проверки результата.

## Управление пользователем

- По умолчанию управление выключено. Hotkeys регистрируются через RegisterHotKey;
  конфликт регистрации показывается как ошибка, без захвата системных сочетаний.
  Конкретное сочетание задаётся параметром/настройкой; MOD_WIN и F12 не используются.
- Три команды этапа: toggle management (предложено Ctrl+Alt+Shift+T), toggle
  floating активного кандидата (Ctrl+Alt+Shift+F), swap/promote активного окна в
  Master (Ctrl+Alt+Shift+Enter). MOD_NOREPEAT, сочетания переназначаемы, конфликт
  регистрации — явная ошибка. Горячие клавиши подключаются на шаге 5.
- Модель уже сохраняет место floating, возвращает его toggle-командой, а promotion
  возвращает floating в tiled и делает первым активным участником. Существующий
  tiled меняется местами с первым активным tiled; floating до текущего master
  после включения уже оказывается первым. Команды для Pending/Inactive/Ineligible
  или interactive окна отвергаются. При невозможности раскладки будущий controller
  должен валидировать изменение на копии и не применять неуспешную команду.
- При включении сохраняются исходные WINDOWPLACEMENT для принятых окон.
  При выключении восстанавливаются только живые окна той же generation, которые
  всё ещё находятся в управляемом состоянии; пользовательские последующие изменения
  видимости и максимизации не отменяются автоматически.
  Это требование шага 5: в текущем CLI шага 4 выход отменяет новые запросы и
  сохраняет итоговые позиции; автоматического восстановления пока нет. Об этом
  сообщают --help и лог при включении --manage-windows.
- WINDOWPLACEMENT хранится и возвращается через Get/SetWindowPlacement. Его
  rcNormalPosition нельзя напрямую передавать в SetWindowPos: системы координат
  для обычного top-level окна различаются.
- Добавляются EVENT_SYSTEM_MOVESIZESTART/END. На START команды для окна
  приостанавливаются; на END оно становится floating до явного возврата в тайлинг.
  Нельзя мешать обычному перетаскиванию или возвращать floating при каждом rescan.
- Hidden/minimized/cloaked временно выходят из active layout, сохраняя порядок.
  Maximized и распознанные fullscreen окна временно не перемещаются. Определение
  fullscreen остаётся эвристикой и проверяется отдельно на borderless-приложениях.
- При отключении выбранного монитора управление приостанавливается до получения
  корректной topology. Не выполняется автоматический перенос всех окон на другой.

## Критерии готовности этапа

| Проверка | Ожидаемый результат |
|---|---|
| 0/1/2/много окон, нечётные размеры, отрицательный origin | Корректные границы и gaps, без потери остатка |
| Неверная доля/gaps, слишком маленькая область, крайние int | Явная ошибка без частичного применения |
| Изменение фокуса и периодический rescan | Стабильный порядок, master не меняется |
| Закрытие между расчётом и отправкой, stale generation | Команда отменяется; новое HWND не получает старую цель |
| Приложение ограничивает размер | Перераспределение min/max, конечный бюджет, затем успех/LayoutInfeasible |
| Grid 300 → 294, неизвестный clamp вниз | Step/свободное место, без ложного min_size и бесконечных re-solve |
| Приложение задерживает обработку | Отдельная диагностика исполнения; message loop отвечает |
| Успешный возврат API без подтверждения | Не считается завершённым размещением |
| Последовательность собственных LOCATIONCHANGE | Нет бесконечного пересчёта и повторных одинаковых команд |
| Ручное перетаскивание и floating toggle | Программа не борется с пользователем |
| Hide/restore, minimize, modal dialog, maximize | Согласованная политика участия и порядок окон |
| 100/125/150/175/200% DPI, панель задач сверху/слева | Верные bounds; canonical target не дрейфует |
| Второй монитор и отрицательные origin | Control HWND внутри выбранного rcMonitor, корректный DPI |
| Ошибка RegisterHotKey, выключение с командой in-flight | Понятный отказ и контролируемое завершение управления |
| Отключение монитора, ошибка API, переполнение событий | Сверка/приостановка, без бесконечной выдачи команд |

Чистый solver проверяется unit/property-style сценариями. Win32 executor —
на собственных fixture windows, включая ограничение размера и задержку UI thread.
Затем вручную проверяются Проводник, браузер, редактор и терминал. Пройденные
проверки подтверждают эти сценарии; универсальное отсутствие ошибок не заявляется.
